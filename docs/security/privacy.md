# Приватность и обработка персональных данных

> Статус документа: 0.2.0. Система обрабатывает фото/видео городской
> инфраструктуры, которые **могут содержать персональные данные** (лица людей,
> автомобильные номера). Анонимизация по-прежнему **не выполняется** — это
> честно отражено в данных и API; в 0.2.0 доступ к неанонимизированным медиа
> ограничен ролевой моделью (см. «Контроль доступа к файлам»). Разделы
> «Рекомендации» не являются реализованными функциями.

## Что хранится

| Данные | Ключ в хранилище | Запись в БД | Анонимизация в MVP |
|---|---|---|---|
| Оригиналы загрузок (фото/видео) | `uploads/{upload_id}/{filename}` | `uploads` + `stored_files` (kind `ORIGINAL`) | нет |
| Кадры из видео / обработанные изображения | `frames/{job_id}/{index:06d}.jpg` | `stored_files` (kind `FRAME`) | **NOT_APPLIED** |
| Кропы детекций | `crops/{job_id}/{detection_id}.jpg` | `stored_files` (kind `CROP`) | **NOT_APPLIED** (явно) |
| Метаданные съёмки (GPS-трек, время, курс, скорость) | — | `uploads.metadata_`, `observations` | нет |

Бинарные данные не хранятся в PostgreSQL — только ключи и метаданные
(см. [storage.md](../integrations/storage.md)).

## Статус анонимизации

Перечисление `AnonymizationStatus` (`app/domain/enums.py`):

| Значение | Смысл |
|---|---|
| `NOT_APPLIED` | Анонимизация не выполнялась (текущее состояние MVP для всех кадров и кропов) |
| `APPLIED` | Анонимизация выполнена успешно |
| `FAILED` | Попытка анонимизации завершилась ошибкой |
| `SKIPPED` | Анонимизация пропущена по политике (например, кадр отклонён quality gate) |

Статус записывается в `stored_files.anonymization_status` для каждого кадра
(`ProcessingPipeline._process_frame`) и кропа (`_store_crop`).

### Честность MVP: NoopPrivacyFilter

`app/application/use_cases/processing/privacy.py`:

```python
class NoopPrivacyFilter:
    async def process(self, jpeg_bytes: bytes) -> PrivacyResult:
        return PrivacyResult(AnonymizationStatus.NOT_APPLIED, jpeg_bytes)
```

Фильтр пропускает кадр без изменений и помечает его `NOT_APPLIED`.
**Система никогда не должна заявлять анонимизацию, которая не выполнялась**:
статус `APPLIED` допустим только после реальной обработки. Запрещено:

- помечать кадры `APPLIED` «авансом» или для совместимости с UI;
- скрывать отсутствие анонимизации в документации/экспортах;
- выдавать кропы за анонимные (они вырезаются из неанонимизированного кадра и
  явно получают `NOT_APPLIED`).

Следствие для эксплуатации: до внедрения реального фильтра доступ к кадрам и
кропам ограничен ролевой моделью (реализовано в 0.2.0, см. ниже), публичная
раздача файлов исключена.

## Точка расширения: PrivacyFilter

```python
class PrivacyFilter(Protocol):
    async def process(self, jpeg_bytes: bytes) -> PrivacyResult: ...

@dataclass(frozen=True)
class PrivacyResult:
    status: AnonymizationStatus
    image_bytes: bytes
    error: str | None = None
```

Подключение реального фильтра (детекция/блюр лиц и номеров):

1. Реализуйте протокол в `app/application/use_cases/processing/` (или отдельном
   infrastructure-модуле, если фильтр обращается к внешнему сервису — по
   образцу изоляции ML, [ADR-0004](../decisions/ADR-0004-ml-provider-isolation.md)).
2. Передайте экземпляр в `ProcessingPipeline(..., privacy_filter=...)` —
   конструктор уже принимает параметр; по умолчанию используется
   `NoopPrivacyFilter`.
3. Семантика статусов: успех → `APPLIED` (и сохранение результата как есть);
   ошибка обработки → `FAILED` + `error` (кадр не должен молча становиться
   «анонимным»); осознанный пропуск → `SKIPPED`.
4. Если анонимизированная версия хранится отдельно от оригинала кадра —
   используйте `StorageObjectKind.ANONYMIZED` (значение уже есть в enum, в MVP
   не используется) и отдельный ключ, например `anonymized/{job_id}/...`.
5. Покройте тестами: unit (статусы/ошибки), integration (pipeline с фильтром),
   API (статус виден в ответах о файлах).

Важно: pipeline сохраняет в `frames/` результат `privacy.image_bytes` — то есть
при `APPLIED` исходный неанонимизированный кадр в хранилище не попадает.
Оригинальная загрузка (`uploads/`) при этом остаётся нетронутой: её обработка —
отдельная политика хранения (см. рекомендации ниже).

## Контроль доступа к файлам

Политики 0.2.0 (реализованы; breaking pre-1.0 — см. CHANGELOG):

- **Медиа-URL только для OPERATOR/ADMIN/SERVICE.** Все ссылки на
  неанонимизированные изображения — `presigned_url` загрузок, `image_url`
  кадров, `crop_url` детекций и эндпоинт `GET /api/v1/files/{key}` — доступны
  только ролям `OPERATOR`, `ADMIN`, `SERVICE`. **VIEWER видит только
  метаданные** (статусы, координаты, приоритеты, текстовые поля); URL медиа
  в его ответах отсутствуют. Обоснование: кадры и кропы не анонимизированы
  (`NOT_APPLIED`) и могут содержать лица/номера — роль просмотра реестра не
  должна давать доступ к изображениям.
- **Аутентификация обязательна для всех файловых операций**; анонимного
  доступа к файлам нет. `GET /api/v1/files/{key}` отдаёт файл через временный
  файл с удалением после ответа.
- **S3-бэкенд**: presigned-ссылки только `GET`, срок действия —
  `S3_PRESIGN_EXPIRES_SECONDS` (по умолчанию 3600 с), публичный host —
  `S3_PUBLIC_ENDPOINT_URL` (см. [storage.md](../integrations/storage.md)).
  Ссылка даёт доступ к конкретному объекту без токена, поэтому: не логировать
  presigned-ссылки, не передавать их третьим лицам, учитывать истечение срока
  в UI. Выдача ссылок проверяет роль **до** генерации.
- **Local-бэкенд** (тесты/лёгкая разработка): presigned-ссылок нет —
  `generate_presigned_url` возвращает относительный путь `/api/v1/files/{key}`,
  который работает только с аутентификацией и ролью OPERATOR+. Защита от
  path traversal — `safe_join` (см. [storage.md](../integrations/storage.md)).
- **Удаление загрузки — только загрузивший пользователь или ADMIN**
  (`DELETE /api/v1/uploads/{id}`): чужую загрузку удалить нельзя (403), даже
  имея роль OPERATOR. Shared-read метаданных сохраняется, владение удалением
  теперь определено явно.
- **Дедупликация по checksum между пользователями не раскрывает чужие
  данные**: при загрузке файла с уже существующим SHA-256 другого
  пользователя возвращается **нейтральная (redacted) запись** — только
  `id` и признак `created: false`, без чужих метаданных (GPS-трек, имя файла,
  владелец) и без медиа-URL. Это закрывает «checksum oracle» (перебор хешей
  для выяснения наличия/метаданных чужих съёмок).
- **Загрузка медиа** — `ADMIN`/`OPERATOR`/`SERVICE` (`OperatorOrAdmin`).
  Роли и полная матрица — [SECURITY.md](../../SECURITY.md).
- ML-сервис читает кадры из хранилища по отдельным credentials с минимальными
  правами (чтение префикса загрузок), не через публичные ссылки
  ([ml-contract.md](../integrations/ml-contract.md) §14).

## Персональные данные в логах

Структурированные логи (structlog, `app/core/logging.py`) содержат процессор
редакции `_redact_processor`: ключи `password`, `password_hash`, `token`,
`access_token`, `authorization`, `secret` (регистронезависимо) заменяются на
`[REDACTED]`. Дополнительно:

- логируются идентификаторы (`request_id`, `job_id`, `actor_id`), коды ошибок и
  метрики — не содержимое изображений и не тела запросов с секретами;
- ML-провайдеры логируют только `request_id` и количество детекций;
- контекст запроса (`request_id`/`job_id`/`actor_id`) пробрасывается через
  contextvars во все записи.

Ограничение: редакция работает по именам ключей верхнего уровня события.
Не кладите секреты/ПДн в произвольные вложенные структуры и строки сообщений.

## Рекомендации по хранению и удалению (НЕ реализовано в MVP)

Ниже — рекомендации для промышленной эксплуатации, а не описание текущих
функций. Автоматических политик retention в MVP нет.

| Объект | Рекомендуемая политика |
|---|---|
| Оригиналы (`uploads/`) | Хранить ограниченный срок (например, 30–90 дней) либо до завершения обработки + аудита; удалять по запросу субъекта данных (см. соображения ниже) |
| Кадры (`frames/`) | Хранить до завершения review-цикла; после — удалять или анонимизировать |
| Кропы (`crops/`) | Минимизировать: кроп может содержать лицо/номер крупным планом; удалять вместе с наблюдением или после экспорта в training-датасет с обезличиванием |
| Анонимизированные версии | Могут храниться дольше оригиналов; статус `APPLIED` обязателен |
| Экспорты (CSV/XLSX) | В MVP отдаются потоком и не сохраняются; при появлении сохранённых экспортов — короткий TTL и контроль доступа |
| Training examples | Содержат ссылки на наблюдения; перед передачей в обучение — обезличивание кадров |

GDPR-подобные соображения (рекомендации; применимость зависит от юрисдикции
эксплуатации — для РФ актуален 152-ФЗ, для ЕС — GDPR):

1. **Правовое основание**: определить основание обработки изображений с ПДн
   (законный интерес / согласие / исполнение договора) до промышленного запуска.
2. **Минимизация**: не собирать больше кадров, чем нужно для инспекции;
   рассмотреть анонимизацию на этапе ingestion (до сохранения в `frames/`).
3. **Права субъектов**: предусмотреть процедуры доступа/удаления данных по
   запросу; текущая модель (ключи + `stored_files`) позволяет найти все объекты
   загрузки/задачи, но автоматического «удалить всё по субъекту» нет — лица/номера
   не индексируются.
4. **Уведомление о инцидентах**: процесс реагирования на утечку кадров с ПДн.
5. **Договоры с обработчиками**: ML-сервис и хранилище — обработчики данных;
   доступ ML к кадрам оформить как обработку по поручению.
6. **Оценка воздействия (DPIA)**: для систем массового наблюдения за публичным
   пространством рекомендуется до запуска.
