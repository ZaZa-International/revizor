# ADR-0005: Взвешенная политика дедупликации / Weighted deduplication policy

- **Статус / Status:** Accepted
- **Дата:** 2026-11-15

## Контекст / Context

Один и тот же физический объект наблюдается многократно: кадры одного проезда,
повторные проезды, разные маршруты. Наивное слияние «всё в радиусе N метров»
склеивает разные объекты (колодец и шкаф рядом), а отказ от дедупликации
размножает дубли активов. Решение должно быть прозрачным (объяснимым для
оператора), настраиваемым и безопасным: сомнительные случаи не должны
автоматически изменять каталог.

## Решение / Decision

Чистая доменная политика `app/domain/deduplication/policy.py` (без I/O);
кандидатов поставляет application-слой через PostGIS-запросы в радиусе.

1. **Взвешенная оценка кандидата** (веса `WEIGHTS`, сумма = 1.0):

   | Фактор | Вес | Score |
   |---|---:|---|
   | spatial | 0.55 | `1 - distance/radius` внутри радиуса, иначе 0 |
   | type | 0.20 | 1.0 при совпадении типа актива, иначе 0 (кандидаты другого типа отбрасываются до скоринга) |
   | temporal | 0.05 | 1.0 в окне `time_window_hours` (2 ч), далее спад; нет данных → нейтральные 0.5 |
   | context | 0.15 | same tracking_id → 1.0; same route → 0.7; иначе 0.3 |
   | visual | 0.05 | embedding/visual similarity при наличии, иначе нейтральные 0.5 |

2. **Пороги** (настройки `DEDUP_MATCH_THRESHOLD=0.70`,
   `DEDUP_POSSIBLE_THRESHOLD=0.45`):
   - `score ≥ 0.70` → `MATCHED` (слияние с лучшим кандидатом);
   - `0.45 ≤ score < 0.70` → `POSSIBLE_MATCH` (кандидат указывается, но актив
     не сливается автоматически — observation остаётся без asset_id и уходит
     в review);
   - `score < 0.45` или нет кандидатов → `NEW_ASSET`.
3. **Неоднозначность никогда не сливается автоматически**: если два и более
   кандидата преодолели match-порог и разница их оценок `< AMBIGUITY_MARGIN
   (0.10)` → `AMBIGUOUS`, слияния нет, требуется человек.
4. **Объяснение сохраняется**: `DeduplicationDecision.explanation` (политика
   `weighted-v1`, веса, конфигурация, факторы лучшего кандидата, топ-5
   кандидатов с оценками и расстояниями, причина решения) персистентно
   записывается в `observations.dedup_explanation` вместе с `dedup_result` и
   `dedup_score`. Каждое решение воспроизводимо и объяснимо постфактум.
5. **Радиус — per-type**: `AssetTypeDef.dedup_radius_m` (колодец 10 м, опора
   12 м, шкаф 8 м, линия 25 м, other 15 м); fallback — `DEDUP_RADIUS_M=15`.
6. **Точка расширения — эмбеддинги**: `CandidateEvidence.embedding_similarity`
   (приоритетнее `visual_similarity`) уже участвует в visual-факторе; когда ML
   начнёт возвращать `embedding` (поле есть в контракте v1.0), фактор станет
   содержательным без изменения структуры политики. Нейтральное значение 0.5
   не искажает оценку при отсутствии данных.
7. Последствия `POSSIBLE_MATCH`/`AMBIGUOUS` для приоритета: актив/наблюдение
   маршрутизируется в `NEEDS_REVIEW` (ADR-0007).

## Последствия / Consequences

- Ложные слияния минимизированы: тип обязателен, радиус ограничен, порог
  консервативный, неоднозначность останавливает автоматику.
- Каждое решение объяснимо: оператор видит факторы и оценки в объяснении;
  аудит и отладка возможны без воспроизведения запросов.
- Политика детерминирована и покрыта unit-тестами (`test_dedup_policy.py`) +
  интеграционными на реальном PostGIS (`test_dedup_integration.py`).
- Цена: часть дублей остаётся несведённой до review (`POSSIBLE_MATCH`);
  это осознанный обмен полноты на безопасность.
- Веса и пороги — эвристика проекта, калибруются настройками; изменение весов
  меняет поведение каталога и требует пересмотра тестов.

## Рассмотренные альтернативы / Alternatives considered

1. **Слияние по радиусу без взвешивания** («ближайший актив того же типа в
   радиусе»): склеивает разные объекты в плотной застройке, необъяснимо;
   отклонено.
2. **Только ML-эмбеддинги (косинусная близость)**: непрозрачно, требует
   обученной модели и embeddings в MVP (их нет), ошибка модели молча меняет
   каталог; отклонено как единственный механизм, оставлено как фактор-расширение.
3. **Только ручная дедупликация**: оператор тонет в дублях при потоковой съёмке;
   отклонено.
4. **Вероятностная модель (логистическая регрессия/байесовское слияние)**:
   требует размеченных данных и усложняет объяснение; отклонено для MVP,
   взвешенная сумма — прозрачная отправная точка.

## Поправки 0.2.0 / Amendments (2026-11-16)

По итогам аудита (DEDUP-1/2/3, GEO-3, REL-5) реализация дедупликации усилена;
сама взвешенная политика (веса, пороги, AMBIGUOUS-правило) не изменилась.

1. **Лимит кандидатов поднят до 50 (DEDUP-1)**: настройка
   `DEDUP_MAX_CANDIDATES=50` (было 10). В плотной зоне (шкафы, радиус 8 м)
   лимит 10 мог отрезать true match, оказавшийся за пределами ближайшей
   десятки, — observation ложно уходил в `NEW_ASSET`. Кандидаты по-прежнему
   ближайшие сверху (`ORDER BY ST_Distance ... LIMIT`).
2. **Батчинг evidence-запросов (DEDUP-2/ARCH-3)**: вместо fan-out'а
   «запрос на каждого кандидата» (22–31 запрос/детекция) evidence собирается
   батчами: последние наблюдения кандидатов — одним запросом
   (`DISTINCT ON` + join jobs для `route_id`), признак `same_route` — одним
   `EXISTS` по всем candidate id; выбираются только нужные колонки (без
   `raw_model_payload`). Цель — ≤ 4 SELECT внутри match при 10 кандидатах;
   решения политики идентичны прежним.
3. **`same_route` — EXISTS по любому наблюдению (DEDUP-3)**: фактор context
   считает маршрут совпавшим, если **любой** job наблюдения актива связан с
   тем же маршрутом (`EXISTS`), а не только последний observation. Прежнее
   поведение занижало context-score при повторных проездах разными job'ами.
4. **Grid advisory lock против конкурентных дублей (REL-5)**: match+insert
   наблюдения выполняется в транзакции кадра под
   `pg_advisory_xact_lock(hashtextextended(...))` по ключу
   «type + grid-ячейка 0.01°» (~1.1 км по широте).
   Два конкурентных pipeline, наблюдающих один физический объект, сериализуются
   в одной ячейке и видят актив друг друга (READ COMMITTED иначе давал оба
   `NEW_ASSET`). **Ограничение границы**: объекты у границы смежных ячеек
   могут попасть в разные ячейки — lock снижает, но не устраняет гонку полностью;
   это coarse-сериализация, а не гарантия уникальности (истина остаётся за
   политикой дедупликации). Полное решение — единый ключ по гео-области или
   Serializable-изоляция, отложено как избыточное для текущих объёмов.
   Lock advisory и транзакционный: не требует новых таблиц и освобождается
   автоматически при commit.
5. **Взаимодействие с GPS accuracy gate (GEO-3)**: если `accuracy_m` точки
   трека хуже `GPS_MAX_ACCURACY_M` (по умолчанию 50 м), геолокация даёт
   `ESTIMATED` вместо `CONFIRMED`. Это влияет на качество точки дедупликации:
   при радиусах 8–25 м точка с погрешностью 1000 м не может считаться
   достоверной — spatial-фактор считается по ней, но пониженный статус/
   confidence геолокации уводит сомнительные случаи в review, а не в
   автоматическое слияние. Отсутствие `accuracy_m` сохраняет прежнее
   поведение (backward compat).

Следствия: дедупликация дешевле по запросам, полнее в плотных зонах и
безопаснее при конкуренции; объяснение решения (`dedup_explanation`) остаётся
машиночитаемым и воспроизводимым.
