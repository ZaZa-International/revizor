# ADR-0009: Идемпотентность загрузки и обработки / Idempotency of uploads and processing

- **Статус / Status:** Accepted
- **Дата:** 2026-11-15

## Контекст / Context

Система живёт в мире повторов: клиент ретраит загрузку при обрыве сети, RQ
повторяет задачу при сбое (ADR-0003), ML может вернуть те же детекции при
переобработке кадра, оператор дважды нажимает «создать задачу». Без
идемпотентности это даёт дубли загрузок, кадров, наблюдений и активов —
каталог загрязняется, статистика искажается.

## Решение / Decision

Идемпотентность обеспечивается на каждом уровне, преимущественно
**ограничениями БД**, а не только логикой приложения:

1. **Загрузки — checksum-unique**: `uploads.checksum_sha256` UNIQUE.
   `UploadService` считает SHA-256 потока; при совпадении возвращает
   существующую загрузку (`created=False`), файл повторно не сохраняется.
   `uploads.storage_key` также UNIQUE.
2. **Кадры — unique (job_id, frame_index)**: `uq_job_frame_index` на
   `job_frames`. Pipeline пропускает кадры со статусом
   `PROCESSED`/`REJECTED`/`SKIPPED` при повторном проходе; запись кадра —
   upsert по индексу.
3. **Детекции — частичный уникальный индекс**:
   `uq_observations_job_detection` на `(processing_job_id, detection_id)`
   `WHERE detection_id IS NOT NULL`. Повторная детекция с тем же
   `detection_id` в той же задаче пропускается
   (`exists_by_job_detection` → `detection_skipped_duplicate`); частичность
   допускает наблюдения без ML-идентификатора (ручные).
4. **HTTP — заголовок `Idempotency-Key`**: для небезопасных POST (uploads,
   jobs, reviews) ключ сохраняется в `idempotency_records` с UNIQUE
   `(key, user_id, endpoint)`; повторный запрос с тем же ключом возвращает
   закэшированные статус и тело ответа (`idempotent_post`,
   `app/api/v1/idempotency.py`). Область ключа — пользователь + эндпоинт.
5. **Задачи — `jobs.idempotency_key` UNIQUE**: повторное создание задачи с
   тем же ключом не плодит дубли.
6. **ML — стабильные идентификаторы**: контракт требует стабильный
   `detection_id` при повторной обработке того же `request_id` (ADR-0004);
   это делает уровень 3 работающим на ретраях.
7. **Повторный запуск pipeline безопасен**: терминальные статусы задачи
   (`COMPLETED`/`CANCELLED`) пропускаются; кадры и детекции дедуплицируются
   уровнями 2–3; повтор не создаёт новых активов/дефектов.

## Последствия / Consequences

- Ретраи клиента, очереди и ML не загрязняют каталог; дедупликация активов
  (ADR-0005) работает с чистыми наблюдениями.
- Гарантии обеспечиваются БД — race condition между параллельными воркерами
  не создаёт дубль (unique violation обрабатывается как «уже есть»).
- Повторная загрузка того же файла экономит место и обработку (возврат
  существующей записи).
- Цена: SHA-256 считается при каждой загрузке (стриминг, приемлемая стоимость);
  `idempotency_records` требует очистки старых записей (политика retention —
  рекомендация, в MVP автоматической очистки нет).
- Клиент должен переиспользовать `Idempotency-Key` при ретрае; новый ключ =
  новая операция (это семантика заголовка, а не баг).

## Рассмотренные альтернативы / Alternatives considered

1. **Только логика приложения (проверка «есть ли уже»)**: race conditions
   между параллельными запросами/воркерами создают дубли; отклонено —
   ограничения БД обязательны.
2. **Redis-ключи идемпотентности**: теряются при flush/рестарте, не переживают
   failover; отклонено в пользу персистентной таблицы.
3. **Дедупликация только по имени файла**: имя ненадёжно (переименования,
   разные файлы с одним именем); отклонено в пользу checksum содержимого.
4. **Отказ от идемпотентности («клиент сам разбирается»)**: перекладывает
   сложность на всех клиентов и ломает ретраи очереди; отклонено.
