# ADR-0002: PostGIS geography, SRID 4326, порядок (lon, lat) / PostGIS geography with SRID 4326

- **Статус / Status:** Accepted
- **Дата:** 2026-11-15

## Контекст / Context

Активы и наблюдения имеют геопривязку (GPS съёмки, ручная коррекция,
map matching). Нужны: поиск активов в радиусе (метры) для дедупликации,
bbox-фильтры карты и аналитики, покрытие территории, расстояния между
наблюдениями. Данные — глобальные WGS84-координаты; точность GPS ограничена
(единицы метров), проекционные искажения на масштабе города недопустимы для
честных метровых расстояний.

## Решение / Decision

1. **PostGIS `geography(POINT, 4326)`** для `assets.location` и
   `observations.location` (GeoAlchemy2 `Geography(geometry_type="POINT",
   srid=4326)`). Запись — `WKTElement(..., srid=4326)`.
2. **SRID 4326 (WGS84)** — единая система координат всей системы: БД, API,
   ML-контракт, GeoJSON карты.
3. **Порядок координат всегда `(longitude, latitude)`** — в API, GeoJSON,
   ML-контракте, внутренних моделях (`app/domain/geospatial/models.py`).
   Валидация диапазонов: `lon ∈ [-180, 180]`, `lat ∈ [-90, 90]`; эвристика
   детектирует перепутанные координаты (похоже на swap) и возвращает подсказку
   `coordinates_appear_swapped`.
4. Расстояния и радиусы — в метрах через функции geography (`ST_Distance`,
   `ST_DWithin`); bbox-фильтры — пересечение с полигоном bbox в 4326.
5. NULL-локация согласована со статусом: `CheckConstraint
   (location IS NULL) = (geolocation_status IN ('UNAVAILABLE','INVALID'))`.
   Статусы геолокации: `CONFIRMED / ESTIMATED / UNAVAILABLE / INVALID`;
   улучшение локации актива — только по рангу статуса и точности
   (`pipeline._location_improves`).

## Последствия / Consequences

- Метровые расстояния честные на любой широте без выбора проекции;
  дедупликация в радиусе (ADR-0005) работает корректно.
- Индексы GiST по geography-колонкам ускоряют радиусные и bbox-запросы.
- Единый порядок (lon, lat) устраняет классический класс ошибок swap;
  контрактные тесты frontend проверяют порядок координат GeoJSON.
- Цена: geography-вычисления дороже geometry; для MVP-объёмов несущественно.
- Тесты обязаны идти на реальном PostGIS (SQLite не поддерживает geography) —
  см. ADR-0011.
- Смена порядка координат или SRID в будущем — ломающее изменение контракта.

## Рассмотренные альтернативы / Alternatives considered

1. **`geometry` с проекцией (например, 3857 или локальная МСК)**: быстрее, но
   метры в 3857 искажаются с широтой; выбор/смена проекции — отдельная
   сложность; отклонено в пользу честных метров geography.
2. **`geometry(POINT, 4326)` без geography**: расстояния в градусах, радиусы
   пришлось бы конвертировать приблизительно; отклонено.
3. **Без PostGIS: float-колонки lon/lat + Haversine в Python**: нет spatial
   индексов и bbox-запросов в SQL, вся геообработка переезжает в приложение и
   не масштабируется; отклонено.
4. **Порядок (lat, lon)**: распространён в бытовых GPS-треках, но противоречит
   GeoJSON/PostGIS `ST_MakePoint(lon, lat)` и ML-контракту; отклонено, swap
   детектируется валидацией.
