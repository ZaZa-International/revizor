# ADR-0008: Append-only reviews и неизменяемые предсказания / Append-only reviews, immutable predictions

- **Статус / Status:** Accepted
- **Дата:** 2026-11-15

## Контекст / Context

Человеческий review — источник истины для эффективного состояния наблюдения,
но ML-предсказания нужны нетронутыми для аудита, анализа качества модели и
формирования обучающих данных. Перезапись предсказаний «поверх» теряет историю
и делает невозможным разбор ошибок модели. Нужен механизм исправлений без
мутаций исходных данных и контролируемый сбор training-примеров.

## Решение / Decision

1. **Reviews — append-only** (`app/domain/reviews/logic.py`,
   `app/application/services/reviews.py`): каждый review — новая запись
   (`reviews`), предыдущие никогда не изменяются и не удаляются. Эффективное
   состояние наблюдения определяет **последний** review.
2. **Оригинальные предсказания неизменяемы**: `observations` хранит исходные
   `object_type`, `condition_class`, `detector_confidence`, `severity`,
   `raw_model_payload` (полный JSON детекции), `model_name`/`model_version`.
   Review не перезаписывает эти поля.
3. **Эффективное состояние — отдельно**: поля `effective_asset_type`,
   `effective_condition`, `effective_severity`, `review_status` вычисляются
   чистой функцией `apply_review(...)` из оригинала + последнего решения:
   - `CONFIRMED` — оригинал подтверждён;
   - `REJECTED` — наблюдение отклонено (`is_rejected`), приоритет 0;
   - `CORRECTED` — применяются корректировки (тип актива/состояние/дефект/
     severity); обязательна хотя бы одна корректировка, корректировки
     допустимы только с `CORRECTED`; коды валидируются против реестров
     (`is_known_asset_type`, `is_known_defect_type`), severity ∈ 1..5;
   - `NEEDS_MORE_INFORMATION` — состояние не меняется, наблюдение остаётся в
     `NEEDS_REVIEW`.
4. **История актива**: изменения состояния/приоритета фиксируются
   `AssetHistoryService` (`condition_history`) с источником изменения
   (`ML_PREDICTION` / `HUMAN_REVIEW` / `MANUAL_EDIT` / `SYSTEM`).
5. **Controlled active learning**: подтверждённые и исправленные наблюдения
   становятся `training_examples` (статусы `PENDING` → `EXPORTED`; связь с
   наблюдением уникальна). Это **сбор** данных для обучения, а не обучение:
   **автоматического retrain нет** — экспорт датасета и запуск обучения
   выполняет ML-команда осознанно, вне backend.
6. Review требует роль `OPERATOR`/`ADMIN`/`SERVICE`; каждое решение аудируется
   (`AuditAction.REVIEW`).

## Последствия / Consequences

- Полный аудит: видно, что предсказала модель, что решил человек и когда;
  ошибки модели разбираемы постфактум.
- Качество модели измеримо: сравнение оригиналов и эффективных состояний
  даёт метрики precision/recall по review-разметке.
- Training-датасет формируется из проверенных человеком данных; статус
  `EXPORTED` предотвращает повторный экспорт.
- Цена: таблица reviews растёт (append-only), эффективное состояние требует
  вычисления/применения последнего review; это осознанная плата за
  неизменяемость.
- Запрет auto-retrain исключает «тихую» деградацию модели на шумных данных и
  неконтролируемые изменения поведения системы.

## Рассмотренные альтернативы / Alternatives considered

1. **Мутабельные наблюдения** (review перезаписывает поля предсказания):
   теряется оригинал и аудит, невозможно измерять качество модели; отклонено.
2. **Версионирование всей строки наблюдения (SCD2)**: избыточно — неизменяемый
   оригинал + append-only reviews дают ту же историю проще; отклонено.
3. **Автоматический retrain по подтверждённым примерам**: неконтролируемое
   изменение модели, риск отравления данных и деградации, требует MLOps-контура;
   отклонено для MVP (сбор примеров — да, обучение — нет).
4. **Хранение корректировок в JSON без структуры**: не валидируется, не
   индексируется, ломает аналитику; отклонено в пользу типизированных полей.
