# ADR-0007: Разделение confidence / severity / priority; прозрачная формула риска / Confidence, severity, priority separation; transparent risk formula

- **Статус / Status:** Accepted
- **Дата:** 2026-11-15

## Контекст / Context

ML-предсказание несёт несколько разных смыслов, которые нельзя смешивать:
уверенность модели в детекции, физическую тяжесть дефекта и очередность работ.
«Низкая уверенность» не означает «проблемы нет» — молча занижать приоритет
неуверенных детекций опасно (пропущенный открытый колодец). Формула приоритета
должна быть объяснима оператору и воспроизводима, а не «чёрным ящиком».

## Решение / Decision

1. **Три независимых понятия**:
   - `confidence` ∈ [0, 1] — уверенность ML-модели в детекции;
   - `severity` ∈ {1..5} | null — физическая тяжесть состояния/дефекта
     (null = не оценивалась; для `ok`/`unknown` дефекта нет);
   - `priority` ∈ [0, 100] — вычисленная очередность реакции + `priority_band`.
2. **Прозрачная версионируемая формула** (`app/domain/risk/scoring.py`,
   `RiskPolicy.version = "1.0"`, настройка `RISK_POLICY_VERSION`):

   ```
   severity_norm    = (severity - 1) / 4          # null → 0.5 (UNKNOWN_SEVERITY_NORM)
   confidence_factor = 0.5 + 0.5 * confidence     # низкая уверенность снижает умеренно, не обнуляет
   priority = clamp(100 * severity_norm * impact_factor * confidence_factor, 0, 100)
   ```

   `impact_factor` — важность типа актива из реестра (`AssetTypeDef`; fallback
   0.5 для неизвестного типа). Все факторы и вычисленное значение сохраняются
   в `RiskAssessment.factors` вместе с `policy_version` — решение объяснимо
   постфактум.
3. **Полосы приоритета**: `HIGH_PRIORITY ≥ 70`, `MEDIUM_PRIORITY ≥ 40`,
   иначе `LOW_PRIORITY` (пороги настраиваемые).
4. **Полоса `NEEDS_REVIEW`** вместо молчаливого занижения: наблюдение без
   review уходит в `NEEDS_REVIEW`, если `confidence < 0.6`
   (`RISK_REVIEW_CONFIDENCE_THRESHOLD`), или severity неизвестна, или
   дедупликация дала `POSSIBLE_MATCH`/`AMBIGUOUS`. Решение
   `NEEDS_MORE_INFORMATION` также удерживает в `NEEDS_REVIEW`.
5. **Review меняет исход**: `REJECTED` → priority 0, `LOW_PRIORITY`;
   подтверждённые/исправленные наблюдения скорятся по эффективному состоянию.
6. **Ручное переопределение с причиной**: `priority_override` (0..100) +
   `priority_override_reason` на активе (PATCH с оптимистичной блокировкой).
   Override имеет приоритет над вычисленным значением и подавляет
   `NEEDS_REVIEW`-маршрутизацию; причина обязательна (валидация сервиса:
   `priority_override_reason is required when overriding priority`) и
   фиксируется в истории изменений.
7. **Это эвристика проекта, НЕ отраслевой стандарт.** Формула, веса и пороги —
   инженерное решение MGTS Infrastructure Intelligence, подлежащее калибровке
   на реальных данных; документация и API не должны представлять её как
   нормативную методику.

## Последствия / Consequences

- Оператор видит, почему объект в той или иной полосе: факторы и версия
  политики сохранены; ручное решение всегда с причиной.
- Неуверенные детекции не теряются: они попадают в review, а не в «низкий
  приоритет».
- Версионирование политики позволяет сравнивать оценки разных периодов и
  мигрировать формулу осознанно.
- Цена: эвристика не калибрована на статистике отказов; пороги могут
  потребовать настройки после эксплуатации; `NEEDS_REVIEW` создаёт нагрузку
  на операторов (осознанный выбор безопасности).
- Смешение понятий запрещено на уровне схем: API отдаёт confidence, severity
  и priority раздельно.

## Рассмотренные альтернативы / Alternatives considered

1. **Единый «risk score» от ML-модели**: непрозрачно, невоспроизводимо без
   модели, смешивает уверенность и тяжесть; отклонено.
2. **priority = severity (без confidence/impact)**: игнорирует важность типа
   актива и неуверенность; отклонено.
3. **Линейное обнуление при низкой уверенности** (`priority *= confidence`):
   молча прячет потенциально опасные объекты; отклонено в пользу умеренного
   множителя 0.5..1.0 + полосы NEEDS_REVIEW.
4. **Нормативная отраслевая методика**: готовой общепринятой формулы для
   drive-by инспекции телеком-инфраструктуры нет; выдавать эвристику за стандарт
   нечестно; отклонено, формула помечена как проектная.
