# ADR-0010: Таксономия как реестр в коде + VARCHAR / Taxonomy as code registry over VARCHAR columns

- **Статус / Status:** Accepted
- **Дата:** 2026-11-15

## Контекст / Context

Типы активов и дефектов будут расширяться: новые классы инфраструктуры, новые
виды повреждений. Классический путь — PostgreSQL enum или справочные таблицы —
требует миграции (и при enum — `ALTER TYPE`, блокировки) на каждое добавление.
Для MVP с частыми итерациями таксономии это тормозит и ML-команду (новые коды
в предсказаниях), и backend. При этом нужна валидация кодов и человекочитаемые
имена.

## Решение / Decision

1. **Реестры в коде — единственный источник истины**:
   - `app/domain/assets/taxonomy.py`: `AssetTypeDef(code, display_name,
     impact_factor, dedup_radius_m)`, `register_asset_type`,
     `get_asset_type`, `is_known_asset_type`, `all_asset_types`;
   - `app/domain/defects/taxonomy.py`: `DefectTypeDef(code, display_name,
     default_severity, applicable_asset_types)`, аналогичные функции.
   Реестры — frozen dataclass'ы в словаре; регистрация при импорте модуля.
2. **Колонки типов — `VARCHAR(64)`**, не PG enum: `assets.asset_type`,
   `observations.object_type`/`effective_asset_type`, `defects.defect_type`.
   **Добавление нового типа не требует миграции БД.**
3. **Валидация на границах приложения**: review-корректировки проверяются
   `is_known_asset_type`/`is_known_defect_type`; ML-контракт принимает открытую
   строку `object_type`/`condition_class` (1..64), канонические коды —
   рекомендация; неизвестный тип не ломает pipeline (risk fallback 0.5).
4. **Поведенческие атрибуты живут в реестре**: `impact_factor` (скоринг,
   ADR-0007) и `dedup_radius_m` (дедупликация, ADR-0005) читаются политиками
   напрямую из определения типа.
5. **Процедуры добавления** задокументированы:
   `docs/development/adding-new-asset-type.md`,
   `docs/development/adding-new-defect-type.md` (регистрация → опциональный
   маппинг состояний → тесты → сид → уведомление ML-команды).
6. Mock-провайдер читает реестр динамически (`all_asset_types()`) — новые типы
   сразу появляются в синтетических детекциях.

## Последствия / Consequences

- Новый тип = один PR с регистрацией и тестами; без миграций, без downtime,
  без координации с DBA. ML может начать слать новый код до регистрации —
  система деградирует мягко (fallback), а не падает.
- Реестр версионируется git'ом: история изменений таксономии = история кода;
  code review контролирует осмысленность impact_factor/радиусов.
- Все инстансы приложения разделяют один реестр из образа — консистентность
  при деплое; разные версии образа могут временно иметь разные реестры
  (приемлемо: коды аддитивны).
- Цена: нет справочника типов в БД — UI не может запросить полный список типов
  с display_name через API (в MVP справочного эндпоинта нет); при появлении
  админ-UI справочник можно expose аддитивно.
- `applicable_asset_types` декларативен (runtime-enforcement применимости
  дефекта к типу актива в MVP нет) — соблюдение на совести регистрации/review.
- Удаление/переименование кода всё равно потребует работы с данными (исторические
  строки хранят старый код); реестр рассчитан на аддитивную эволюцию.

## Рассмотренные альтернативы / Alternatives considered

1. **PostgreSQL enum (`CREATE TYPE ... AS ENUM`)**: каждый новый код —
   `ALTER TYPE ... ADD VALUE` (нельзя в транзакции с использованием,
   блокировки, отдельная миграция); удаление значений практически невозможно;
   отклонено.
2. **Справочные таблицы + FK**: строгая ссылочная целостность, но нужны
   миграции/сиды на каждый тип, джойны в каждом запросе, админ-UI для
   управления; для MVP избыточно; отклонено (может быть добавлено позже без
   смены колонок).
3. **Константы, размазанные по коду**: нет единого места, атрибуты
   (impact_factor, радиус) дублируются; отклонено в пользу единого реестра.
4. **Внешний конфиг (YAML/БД-настройки) без кода**: теряется типизация и
   review-контроль поведенческих атрибутов; отклонено — реестр именно код.
