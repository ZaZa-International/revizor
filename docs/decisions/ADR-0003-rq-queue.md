# ADR-0003: RQ вместо Celery для MVP + inline-режим / RQ over Celery for MVP, inline queue mode

- **Статус / Status:** Accepted
- **Дата:** 2026-11-15

## Контекст / Context

Обработка загрузки (извлечение кадров, quality gate, privacy-фильтр, инференс,
дедупликация, скоринг, персистентность) — длительная задача (до 2000 кадров,
таймаут задачи 1800 с). Её нельзя выполнять внутри HTTP-запроса. Нужна очередь
с воркером, ретраями и наблюдаемостью. Redis уже присутствует в стеке
(rate limiting, кэш). Команда маленькая, эксплуатационная сложность критична.

## Решение / Decision

1. **RQ (Redis Queue)** как очередь продакшена: `rq>=3`, очередь `processing`
   (`RQ_QUEUE_NAME`), воркер — отдельный процесс `python -m app.workers.worker`
   (сервис `worker` в docker-compose).
2. Задача ставится по import-path (`app.workers.tasks.processing.process_upload_task`),
   чтобы API-процесс не импортировал pipeline-код при enqueue. Sync-обёртка
   задачи строит изолированный event loop, engine БД и провайдеры на каждое
   выполнение.
3. **Ретраи через планировщик RQ**: `Retry(max=RQ_RETRY_MAX=3,
   interval=[10, 30, 60])` — отложенные повторные попытки выполняет RQ
   scheduler; `job_timeout=1800`, `result_ttl=86400`. Повторная обработка
   безопасна благодаря идемпотентности pipeline (ADR-0009).
4. **Абстракция `JobQueue`** (`application/interfaces/queue.py`):
   `enqueue_processing(job_id)`, `queue_length()`, `close()`. Две реализации:
   `RQJobQueue` и `InlineJobQueue`; выбор — `QUEUE_MODE` (`rq` | `inline`)
   через фабрику.
5. **Inline-режим для тестов и dev**: `InlineJobQueue` выполняет pipeline
   в процессе вызова (в тестах — синхронно с запросом, без воркера и race
   conditions; в dev — `QUEUE_MODE=inline` для запуска без воркера).
   **Не для production**: тяжёлая обработка не должна идти внутри HTTP-запроса.
6. Отмена задачи — кооперативная: pipeline проверяет статус `CANCELLED` каждые
   10 кадров; повторный enqueue завершённой/отменённой задачи — no-op.

## Последствия / Consequences

- Минимум движущихся частей: один Redis, один воркер-процесс, без broker
  кластеров и отдельных result-бэкендов.
- Тесты детерминированы: inline-очередь + mock ML дают полный pipeline внутри
  теста без асинхронных ожиданий воркера.
- Ретраи с нарастающими интервалами переживают кратковременную недоступность
  ML/БД; идемпотентность исключает дубли при повторе.
- Ограничения RQ осознаны: нет приоритетов/маршрутизации очередей из коробки,
  нет cron-планировщика задач (scheduler используется только для ретраев),
  воркеры — процессы (масштабирование репликами). Для MVP достаточно.
- `queue_length()` в inline-режиме всегда 0 — метрика длины очереди в этом
  режиме неинформативна.

## Рассмотренные альтернативы / Alternatives considered

1. **Celery**: мощнее (приоритеты, routing, beat, chains), но тяжелее в
   эксплуатации и настройке (broker/result backend, сериализация, пулы),
   избыточен для одной очереди с одной задачей; отклонено для MVP.
2. **Dramatiq / arq / SAQ**: разумные альтернативы; arq/SAQ async-native, но
   экосистема и зрелость ретраев/мониторинга у RQ выше при сопоставимой
   простоте; отклонено в пользу RQ.
3. **FastAPI BackgroundTasks / asyncio.create_task**: нет персистентности,
   ретраев и переживания рестарта; задача теряется при падении процесса;
   отклонено (inline-режим — осознанное исключение только для тестов/dev).
4. **Внешний брокер (RabbitMQ/Kafka)**: отдельный кластер ради одной очереди;
   отклонено — Redis уже в стеке.
