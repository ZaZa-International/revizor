# ADR-0001: Модульный монолит с четырьмя слоями / Modular monolith with four layers

- **Статус / Status:** Accepted
- **Дата:** 2026-11-15

## Контекст / Context

MVP системы инспекции телеком-инфраструктуры по фото/видео: загрузка медиа,
очередь обработки, ML-инференс (внешний), дедупликация, скоринг риска,
review-цикл, карта, аналитика, экспорты. Команда небольшая, срок вывода MVP
короткий; доменная логика (геообработка, дедупликация, риск, состояния) сложная
и будет эволюционировать. Нужно выбрать архитектурный стиль, который не
утопит MVP в инфраструктурной сложности, но сохранит заменяемость внешних
интеграций (ML, хранилище, очередь) и тестируемость домена.

## Решение / Decision

Один deployable-монолит (FastAPI-приложение + отдельный процесс воркера из той
же кодовой базы) с четырьмя слоями и строгим направлением зависимостей:

```
api → application → domain ← infrastructure
```

1. **`app/domain/`** — чистый Python: enum'ы, реестры типов, политики
   (dedup, risk, condition, review, state machine), геодоменные модели.
   Никаких импортов FastAPI, SQLAlchemy, ML-фреймворков, boto3. Вся логика
   решений — здесь, детерминированная и покрытая unit-тестами.
2. **`app/application/`** — use cases (pipeline обработки) и сервисы
   (uploads, jobs, reviews, deduplication, geolocation, risk, exports, …),
   оркестрирующие домен и порты. Порты — Protocol-интерфейсы
   `MLProvider`, `ObjectStorage`, `JobQueue` (`application/interfaces/`).
3. **`app/infrastructure/`** — реализации портов: SQLAlchemy-репозитории и
   модели, S3/local хранилище, RQ/inline очередь, mock/http ML-провайдеры.
   Единственное место, где живут внешние зависимости.
4. **`app/api/`** — тонкие FastAPI-роутеры: валидация входа, RBAC-зависимости,
   вызов сервисов, сериализация ORM → Pydantic-схемы (`app/schemas/`,
   `api/v1/serializers.py`). ORM-модели никогда не отдаются наружу напрямую.

Сквозные модули: `app/core/` (security, logging, metrics, exceptions,
ratelimit, middleware), `app/config.py` (pydantic-settings), `app/workers/`
(точки входа RQ-задач). Выбор реализаций — фабрики по настройкам окружения.

## Последствия / Consequences

- Домен тестируется без БД и сети (108 unit-тестов); политики прозрачны и
  версионируются.
- Внешние интеграции заменяются без правки домена: mock ↔ http ML,
  s3 ↔ local storage, rq ↔ inline queue (см. ADR-0003, ADR-0004, ADR-0006).
- Один репозиторий, один образ, простые транзакции и деплой; воркер масштабируется
  отдельно от API горизонтально.
- Границы слоёв enforced только дисциплиной и code review (импорты не запрещены
  линтером механически); нарушение границ — блокирующее замечание на review
  (см. CONTRIBUTING.md).
- При будущем выделении сервисов (например, ML уже вынесен) швы портов готовы;
  сам монолит не придётся переписывать.

## Рассмотренные альтернативы / Alternatives considered

1. **Микросервисы с первого дня** (отдельные сервисы загрузки, обработки,
   каталога, review): отклонено — распределённые транзакции, версионирование
   внутренних контрактов, эксплуатационная сложность не окупаются на MVP с
   одной командой; единственный реально внешний компонент (ML) и так вынесен
   за контракт (ADR-0004).
2. **CRUD-монолит без слоёв** (логика в роутерах/сервисах с ORM): отклонено —
   доменные политики (дедупликация, риск) размазываются по HTTP-слою,
   тестируются только через БД, замена интеграций требует переписывания.
3. **Гексагональная архитектура с отдельными пакетами/монорепой и DI-фреймворком**:
   избыточно для MVP; Protocol-порты + фабрики дают ту же заменяемость без
   дополнительного фреймворка.
