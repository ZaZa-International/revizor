# ADR-0004: Изоляция ML-провайдера и контракт v1.0 / ML provider isolation and contract v1.0

- **Статус / Status:** Accepted
- **Дата:** 2026-11-15

## Контекст / Context

Инференс (детекция объектов инфраструктуры и их состояния) выполняет ML-команда
своим стеком (модели, GPU, фреймворки). Backend не должен тянуть ML-зависимости,
GPU-требования и цикл релизов моделей. При этом для демо и тестов нужен
работающий pipeline без реального ML. Формат обмена должен быть стабильным,
версионируемым и проверяемым автоматически.

## Решение / Decision

1. **Единственная точка связности — протокол `MLProvider`**
   (`app/application/interfaces/ml_provider.py`): `health`, `model_info`,
   `infer_image`, `infer_batch`, `close`. Домен и use cases знают только протокол.
2. **Две реализации**: `MockMLProvider` (детерминированные синтетические
   детекции для демо/тестов; честно помечен как не-инференс) и `HTTPMLProvider`
   (клиент внешнего сервиса). Выбор — `ML_PROVIDER` (`mock` | `http`) через
   фабрику `build_ml_provider`.
3. **Контракт v1.0** — эталон `docs/integrations/ml-contract.md`:
   - Pydantic-модели `app/schemas/ml.py` — источник истины; `schema_version:
     Literal["1.0"]`, `extra="forbid"`;
   - JSON Schema (draft 2020-12) в `contracts/ml/*.schema.json` + эталонные
     примеры `contracts/ml/examples/`;
   - контрактные тесты (`tests/contracts/test_ml_contract.py`) проверяют
     согласованность схем, примеров и моделей;
   - эндпоинты `/v1/health`, `/v1/model-info`, `/v1/infer`, `/v1/infer/batch`.
4. **Изображения не передаются по HTTP**: запрос содержит `image.storage_key`
   в общем S3-хранилище; ML-сервис читает кадр сам (отдельные credentials,
   приватная сеть).
5. **Таксономия ошибок**: `MLTimeoutError` / `MLUnavailableError` (повторяемые),
   `MLContractError` / `MLInferenceError` (неповторяемые). HTTP-провайдер:
   `1 + ML_HTTP_RETRIES` попыток на таймауты/connect/5xx с экспоненциальным
   backoff + jitter; 4xx никогда не повторяются; нарушения контракта
   (request_id, bbox, schema_version, уникальность detection_id) →
   `MLContractError`.
6. **Идемпотентность**: `request_id` — ключ запроса; `detection_id` стабилен
   при повторе; backend дедуплицирует по `(job_id, detection_id)` (ADR-0009).
7. **Никаких ML-фреймворков в backend-зависимостях**; обновления модели
   (`model.version`) не требуют изменения контракта, ломающие изменения формата —
   только через новый `schema_version` и префикс `/v2`.

## Последствия / Consequences

- Backend деплоится и масштабируется независимо от ML; ML-команда релизит
  модели без участия backend.
- Демо и полный тестовый pipeline работают без GPU и без ML-сервиса
  (mock детерминирован по `request_id`).
- Контракт проверяется в CI автоматически; расхождение схем/примеров/моделей
  ломает сборку — это намеренно.
- Сетевой hop к ML добавляет латентность и требует ретраев/таймаутов; цена
  принята ради изоляции.
- Mock не оценивает реальное содержимое кадра — результаты демо нельзя
  выдавать за реальный инференс (дисклеймер в контракте §13).
- Аутентификация backend ↔ ML в v1.0 отсутствует (доверенная приватная сеть);
  API-ключ может быть добавлен аддитивно.

## Рассмотренные альтернативы / Alternatives considered

1. **Инференс внутри backend (torch/onnxruntime в процессе)**: ML-зависимости,
   GPU-образы, связанный релизный цикл, деградация API при тяжёлом инференсе;
   отклонено.
2. **gRPC вместо HTTP/JSON**: строже и быстрее, но сложнее отладка/примеры/
   контрактные тесты и порог входа для ML-команды; выигрыш несущественен при
   передаче ссылок вместо байтов; отклонено для MVP.
3. **Прямая интеграция с конкретным ML-фреймворком/сервисом без контракта**:
   неявный формат, невозможность mock-тестов, ломается при каждом релизе модели;
   отклонено.
4. **Очередь задач инференса (Kafka/RabbitMQ) вместо синхронного HTTP**:
   асинхронность усложняет pipeline и ретраи; для покадрового инференса с
   таймаутами синхронный HTTP проще; отклонено для MVP.
